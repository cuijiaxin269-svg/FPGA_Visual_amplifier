# 证据驱动的工程交接

适用于包含多轮源码、位流、固件及板端实验的工程，目标是让下一位开发者确认“什么版本通过了什么测试”，并定位下一项需要补证的工作。

## 输入与使用流程

1. 为候选版本收集源码清单、工具版本、硬件型号、bit/XSA/初始化文件/ELF 的哈希以及测试目录。完成判据：每个测试有唯一的候选版本，无法关联的记录标为历史或来源未知。
2. 将证据区分为主机测试、RTL 仿真、综合实现、板内读回、物理输入/显示、冷启动。完成判据：结论表的每一项都写明层级和原始文件。
3. 对照时间、参数和哈希处理相互矛盾的笔记。旧 README 可以解释接口，但不能覆盖较新的验证记录；更新结论时保存旧事实。完成判据：每个冲突有“旧条件—新观察—采用依据”。
4. 分别记录当前磁盘包与最后已知板上状态。断电、复位或重新下载会使易失状态失效。完成判据：交接者能知道哪些是已封存材料，哪些必须现场重新读回。
5. 写出一个可核查的下一步，例如“用本候选完整上电验证三个视图”，而不是笼统的“继续测试”。完成判据：该步的输入、预期输出和停止条件明确。

可直接复用的交接表字段：`version / source_hash / artifact_hash / tool_version / test_input / parameters / evidence_path / validation_level / passed_or_pending / limitation / next_action`。

## 来源与已验证效果

原工程 [交接技能快照](references/original_handoff.txt) 记录了旧 DDR clip 因现场变化失效、旧 README 与较新实验状态不一致等情况，由此形成按证据与时间判定的交接规则。

现有 v18 数据将 32 分钟观察绑定到指定 ELF/bit；v19 数据把一次 QSPI 冷启动绑定到另一 ELF。通过这一方法可以明确：v18 的长稳不能计为 v19 长稳，调试器辅助交接也不能计为真实冷启动。对应材料见 [证据索引](../report/evidence_index.md)。本次文档整理应用了这一方法，未对当前板上状态作推断。

## 失效条件和局限

哈希一致只证明文件身份，不证明功能正确。缺少运行绑定信息时不能从目录名推断版本。读回寄存器也可能具有清除状态等副作用，现场观察前需核对寄存器语义。此流程在本项目中有实际材料支持，尚未开展独立队伍或其他板卡上的复用试验。
