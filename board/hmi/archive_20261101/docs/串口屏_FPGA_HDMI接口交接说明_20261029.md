# 串口屏 / FPGA / HDMI 接口交接说明

版本：V1.0 · 2026-10-29  
对应屏端 Git 提交：`bafc55f`  
交接对象：负责 Zynq/FPGA 控制、相机及 HDMI 显示的同学

## 1. 先看这几项

当前串口屏负责发送操作请求，板端负责执行并回传真实状态。屏幕本身不处理相机图像，也不通过串口传输 HDMI 图像或波形数据。

**板端优先完成以下三项，才能实现完整联动：**

1. 新增 `VIEW 0/1/2`，接入实际工程原有的画面切换通路，分别显示原画面、放大画面、详细参数。
2. 把相位增益 α 的有效范围从旧固件的 `0..30` 扩展为 `0..50`，同步检查命令解析、参数校验及算法/HLS 门限。
3. 增加发往串口屏的原生状态更新指令。原有的 `OK ...`、`ERROR ...` 终端日志不能直接更新屏幕状态。

| 功能 | 当前串口屏 | 已核对的 2026-10-25 交接固件 | 板端需完成 |
|---|---|---|---|
| 原画面 / 放大画面 / 详细参数 | 发送 `VIEW 0/1/2` | 没有该命令 | 新增解析，接入实际显示切换 |
| 相位增益 α | 整数 `0..50`，默认 12 | 解析及算法门限为 30 | 全链路支持 50，验证边界 |
| 相机曝光 | 整数 `1..898` 行，默认 320 | 有接口，要求 STOP/idle；下一次 START/RECORD 应用 | 保留时序约束，回传接受与生效状态 |
| START / STOP | 一个切换按钮，按下发送 | 有命令，STOP 为异步请求 | 对接实际启停，完成后回传状态 |
| 状态确认 | 有四组独立等待/超时状态 | 输出普通终端日志 | 转换为本文第 5 节的屏幕指令 |

本文描述的是**当前已下载到串口屏的版本**。已验证屏端原生事件、串口字节及状态控件；**尚未完成 FPGA、相机和 HDMI 联调，也未进行真人手指触摸验收**。

## 2. 接线与串口参数

### 2.1 运行参数

| 项目 | 约定 |
|---|---|
| 串口屏 | `TJC1060X570_011C`，1024 × 600 |
| 工作波特率 | **115200 bit/s** |
| 数据格式 | **8N1**：8 位数据、无校验、1 位停止位 |
| 屏 → 板端 | ASCII 命令，每条以 **CR LF，即 `0D 0A`** 结束 |
| 板端 → 屏 | TJC 原生 ASCII 指令，每条以 **三个原始字节 `FF FF FF`** 结束 |
| 当前 PC 维护口 | `COM3`，CH340；仅表示本机下载/测试端口 |
| 下载波特率 | `921600`；**运行通信仍用 115200** |

**两个方向的结束符不同，不能互换。**

逻辑连接关系：

```text
串口屏 TX  ─────→  板端 UART RX
串口屏 RX  ←─────  板端 UART TX
串口屏 GND ────── 板端 GND
```

具体 UART 实例、连接器针脚、屏幕供电要求及双方信号电平，需由硬件负责人按实际板卡确认。当前工程证据不能确定这些物理信息；请区分屏幕供电电压、UART 信号电平与 RS-232 接口。

### 2.2 谁负责执行

建议由已有的板端控制软件统一接收串口请求，再调用现有 FPGA/相机/显示控制接口。若实际工程采用其他架构，保留本文的命令及状态语义即可。

HDMI 三种模式应复用现有实体按钮使用的控制通路，切换时机按实际视频链路处理，建议在帧边界生效。**本文没有指定或假定寄存器地址。**

“详细参数”页面由 HDMI 端排版，参数来自板端真实状态；当前串口屏没有额外发送波形、频谱或参数列表的协议。

## 3. 屏 → 板端：全部业务命令

以下代码块中的 `\r\n` 表示两个实际字节 `0D 0A`，不是发送反斜杠及字母。

| 实际命令格式 | 含义 | 当前屏端触发方式 |
|---|---|---|
| `VIEW 0\r\n` | HDMI 切到原画面 | 对应模式按钮松开时 |
| `VIEW 1\r\n` | HDMI 切到放大画面 | 对应模式按钮松开时 |
| `VIEW 2\r\n` | HDMI 切到详细参数 | 对应模式按钮松开时 |
| `ALPHA n\r\n` | 设置相位增益，整数 `0..50` | 加减、预设、滑条松开或数字键盘确认 |
| `EXPOSURE n\r\n` | 提交曝光行数，整数 `1..898` | 仅曝光区“应用”按钮松开时 |
| `START\r\n` | 请求开始连续运行 | 合并启停按钮当前显示 START 时按下 |
| `STOP\r\n` | 请求停止运行 | 合并启停按钮当前显示 STOP 时按下 |

无地址字段、序号或自定义校验字段。命令大写，参数是十进制整数，命令与参数间为一个 ASCII 空格。

### 3.1 可用于抓包比对的字节

| 文本 | 十六进制字节 |
|---|---|
| `VIEW 0\r\n` | `56 49 45 57 20 30 0D 0A` |
| `VIEW 1\r\n` | `56 49 45 57 20 31 0D 0A` |
| `VIEW 2\r\n` | `56 49 45 57 20 32 0D 0A` |
| `ALPHA 12\r\n` | `41 4C 50 48 41 20 31 32 0D 0A` |
| `ALPHA 50\r\n` | `41 4C 50 48 41 20 35 30 0D 0A` |
| `EXPOSURE 320\r\n` | `45 58 50 4F 53 55 52 45 20 33 32 30 0D 0A` |
| `START\r\n` | `53 54 41 52 54 0D 0A` |
| `STOP\r\n` | `53 54 4F 50 0D 0A` |

### 3.2 接收端要求

- 按行缓存，收到完整 `CR LF` 后解析；正确处理一次接收多条命令，以及一条命令被拆成多次接收。
- 严格检查命令、参数数量及数值范围；拒绝额外参数、负数、非法字符和越界值。
- 建议业务命令接收缓冲区至少 64 字节。超长行应丢弃到下一处行结束，避免污染后续命令。
- `VIEW`、`ALPHA`、`EXPOSURE` 为绝对设定值；重复请求应保持相同目标。`START`、`STOP` 也应按明确的启动/停止语义处理，不能在板端再次解释成“翻转状态”。
- `START` 不带持续时间；当前屏端不发送 `RECORD`、`CAMERA`、`SHUTTER_US`、`GAIN`、`BAND`、`ROI` 或 `OVERLAY`。
- 屏幕也可能发送 TJC 原生二进制应答，见第 6 节；不能把整条 RX 字节流都当成 ASCII 业务命令。

## 4. 操作行为与参数含义

### 4.1 显示模式

“原画面 / 放大画面 / 详细参数”控制的是 **HDMI 输出内容**，不代表切换串口屏自己的主页面。

模式按钮在按下时立即取消旧高亮、显示新高亮，在松开时才发送 `VIEW n`。高亮表示用户选择，只有板端完成切换并回传确认，状态才应显示 `APPLIED`。

### 4.2 相位增益 α

- 范围 `0..50`，默认 12，预设为 `0 / 12 / 50`。
- 加减和预设操作发送当前值；在上下限继续点击加减，也可能重复发送相同边界值。
- 拖动滑条只更新本地数值，松开后发送一次。
- 点击数值进入数字键盘，合法值确认后保存并发送一次 `ALPHA n`。
- **α 是相位增益，不表示图像宽高的几何放大倍数，也不控制放大区域位置。**

旧交接固件 `motion60.c` 只接受到 30，算法链路也存在 `alpha <= 30` 门限。不能只放宽串口解析器：需同步检查算法、HLS 及验证程序；若限制已综合进 PL，则需更新相应位流。特别验证 `30 / 31 / 50` 的实际生效情况。

### 4.3 相机曝光

- 单位是**传感器曝光行数**，整数 `1..898`，默认 320。
- 加减、滑条和数字键盘确认只保存本地设定；必须按“应用”才发送 `EXPOSURE n`。
- 已核对的固定传感器模式约为 `18.2 μs/行`，320 行约 `5.824 ms`，898 行约 `16.3436 ms`。更换传感器模式后应重新核对行时间。
- 旧固件仅在停止且空闲时接受；运行、处理忙或仍有待完成任务时拒绝。
- 旧固件中此接口受 `MOTION60_CAMERA_CONTROLS` 编译条件控制，需确认实际固件启用了相机控制功能。
- 接受后先保存请求值，**下一次 START/RECORD 才配置相机**。当前屏幕只提供 START。

推荐联调顺序：

```text
按 STOP
→ 等待板端确认实际停止、相关任务处理完成
→ 调整曝光，按“应用”
→ 板端接受，回传 QUEUED
→ 按 START
→ 板端配置相机，核对实际读回值
→ 回传曝光 APPLIED，并按真实运行情况回传 RUNNING
```

不能把“收到 STOP”当作已经空闲，不能连续盲发 `STOP → EXPOSURE → START` 或用固定延时替代真实完成判断。当前屏端不会自动串联这三条命令。

### 4.4 START / STOP 合并按钮

| 时刻 | 屏幕发送 | 本地下一次操作 |
|---|---|---|
| 初始状态按下 START | `START\r\n` 一次 | 按钮变成 STOP |
| 松开 | 无 | 保持 STOP |
| 再次按下 STOP | `STOP\r\n` 一次 | 按钮变成 START |
| 松开 | 无 | 保持 START |

按钮保存的是**上次请求状态**，不是板端已确认状态。`runreq=1` 表示下一次按钮操作为 STOP，`runreq=0` 表示下一次为 START。

START 被拒绝时，板端应报告错误并按真实状态修正按钮；STOP 只有完成停机和必要的任务收尾后才回传 `STOPPED`。旧固件的 `OK STOP requested` 只表示收到了请求。

### 4.5 数字键盘

两类数值共用临时输入页，支持最多三位数字、清空、退格、取消和确认。输入首位数字替换原值；空输入或越界值不能提交。取消不改变原值，不发送业务命令。增益确认会发命令，曝光确认不会发命令。

## 5. 板端 → 屏：状态回传

### 5.1 发送规则

使用 **TJC 原生属性赋值指令**。下面每一行都是一条独立指令，必须各自追加三个原始字节 `0xFF`。

例如确认画面切换：

```text
ASCII: page0.vstatus.txt="APPLIED"
末尾:  FF FF FF
```

不要发送字面文本 `"FF FF FF"`，不要以 `CR LF` 代替结束符，不要把多条属性赋值只加一个结束符。普通 `OK START\r\n` 或自定义 `ACK START\r\n` 不会被当前屏幕解析为状态更新。

### 5.2 状态对象

| 功能 | 状态文本 | 确认计时器 | 屏端初始状态 |
|---|---|---|---|
| 画面切换 | `page0.vstatus.txt` | `page0.vack.en` | `SELECT` |
| 相位增益 | `page0.astatus.txt` | `page0.aack.en` | `SET` |
| 相机曝光 | `page0.estatus.txt` | `page0.eack.en` | `SET` |
| 启停 | `page0.rstatus.txt` | `page0.rack.en` | `READY` |

四组状态独立。发出操作后，该组变为 `WAIT ACK` 并启动 3000 ms 计时器；未确认则变为 `NO ACK`。**超时不自动重发，也不撤销本地选择或按钮请求。**

计时器属于主页面；切到数字键盘后，不能把它视为持续运行的全局 3 秒超时。返回主页面时，仍为 `WAIT ACK` 的项目会重新计时。

状态字段最大 16 个字符，建议使用下列短 ASCII 文本：

| 文本 | 含义 |
|---|---|
| `SELECT` / `SET` / `READY` | 本地待选择、待设定或按钮可操作；不是板端状态确认 |
| `WAIT ACK` | 请求已发出，等待板端确认 |
| `NO ACK` | 等待超时，不能据此判断操作成功或失败 |
| `QUEUED` | 曝光已接受，但尚未配置到传感器 |
| `APPLIED` | 对应操作实际生效 |
| `RUNNING` / `STOPPED` | 板端真实运行 / 停止状态 |
| `REJECTED` / `BUSY` / `ERROR` | 建议的拒绝、忙或失败提示，由板端写入 |

### 5.3 成功回传示例

以下完整示例适用于**当前处于主页面 `page0`**。若数字键盘正在打开，按第 6 节处理私有控件。

画面完成切换：

```text
page0.vack.en=0
page0.vstatus.txt="APPLIED"
```

相位增益已在算法侧生效：

```text
page0.aack.en=0
page0.astatus.txt="APPLIED"
```

曝光请求被接受，等待下次启动：

```text
page0.eack.en=0
page0.estatus.txt="QUEUED"
```

START 时，相机配置完成且读回匹配后，再发送：

```text
page0.estatus.txt="APPLIED"
```

实际进入运行：

```text
page0.rack.en=0
page0.rstatus.txt="RUNNING"
page0.runreq.val=1
page0.run.val=1
```

实际停止并完成必要收尾：

```text
page0.rack.en=0
page0.rstatus.txt="STOPPED"
page0.runreq.val=0
page0.run.val=0
```

每个示例的**每一行末尾均需加 `FF FF FF`**。不能在解析到请求的瞬间就无条件回传 `APPLIED`、`RUNNING` 或 `STOPPED`。

### 5.4 拒绝及异步状态

- 曝光因运行中被拒绝：停止 `eack`，将 `estatus` 设为 `BUSY` 或 `REJECTED`，不发送 `QUEUED/APPLIED`。
- START 失败且设备仍停止：停止 `rack`，将 `rstatus` 设为 `ERROR/REJECTED`，把 `runreq` 和主页面 `run` 修正为 0。
- STOP 未完成：保持等待；只有实际停止后才回传 `STOPPED`。操作耗时超过屏端等待时间时可能出现 `NO ACK`，后续仍可用真实结果更新。
- 真实参数被限制或操作失败时，不应将本地目标值当成实际值发布到 HDMI。当前 HMI 数字主要表示用户设定值，详细读回信息可放在 HDMI 参数页。
- 若保留实体按钮，实体按钮引发的状态变化也应同步给串口屏，避免下一次触摸操作与真实状态错位。

## 6. 数字键盘、启动与接收兼容

### 6.1 跨页面回传

| HMI 页面 | ID | 用途 |
|---|---|---|
| `page0` | 0 | 唯一主操作页 |
| `page1` | 1 | 原开机动画，播放完自动进入主页面 |
| `keypad` | 2 | 临时数字输入 |

以下对象为全局作用域，可使用带页面名的路径访问：

```text
page0.mode.val
page0.alpha.val
page0.exposure.val
page0.runreq.val
page0.edittarget.val
page0.vstatus.txt
page0.astatus.txt
page0.estatus.txt
page0.rstatus.txt
```

`run` 按钮、模式按钮、滑条、预设按钮及四个计时器属于主页面私有控件。**不能假定数字键盘页打开时，对这些私有对象的写入仍然有效。**

推荐处理：

1. 状态结果先写对应全局状态文本；实际启停状态同步写 `page0.runreq.val`。
2. 当前为主页面时，再停相应计时器、同步私有按钮。全局状态文本先改为非 `WAIT ACK`，可避免返回主页面时重新等待该操作。
3. 当前为数字键盘时，暂缓私有控件写入；返回主页面后，页面脚本会依据全局值同步模式、滑条、预设及启停按钮。
4. 不要强制跳转主页面来处理回传，以免丢失用户正在输入的草稿。

如需判断当前页面，可发送原生指令 `sendme`，末尾仍为 `FF FF FF`；响应格式：

```text
66 <页面ID，一个字节> FF FF FF
```

例如主页面为 `66 00 FF FF FF`。这是 TJC 二进制响应，不是业务命令。

### 6.2 上电与状态同步

屏幕保留开机动画，启动时**不会自动发送业务命令**。本地初始值为：

```text
mode=255        未选择/未确认 HDMI 模式
alpha=12        本地默认相位增益
exposure=320    本地默认曝光行数
runreq=0        按钮初始显示 START
```

这些值不是板端读回结果，`READY` 也不表示板端已停止。

板端或屏幕单独重启后，应等待屏幕初始化完成，再同步实际运行状态；需要同步模式、参数时，写相应全局值，并在主页面同步对应私有控件。主页面加载脚本会做一次同步，但**在主页面停留期间，仅写全局参数不会自动触发滑条或高亮刷新**。

实际模式按钮名为 `raw / mag / panel`，增益滑条为 `hgain`，预设为 `p0 / p12 / p50`，曝光滑条为 `hexp`。同步时应按全局值设置对应私有对象，并保证模式与预设互斥。

不要在数字键盘编辑过程中用周期性状态轮询覆盖用户草稿或未提交的曝光设定。当前协议没有独立的“读取全部状态”业务命令，初始化同步由板端适配层主动实现。

### 6.3 原生应答与并发

当前屏幕实测 `bkcmd=2`，即原生指令出错时会返回错误应答；测试程序临时设过 3，结束后已恢复。

因此板端 RX 必须区分业务 ASCII 行与 TJC 原生二进制包。如果使用 `sendme`、`get` 或开启更多原生应答，还需解析相应包型。例如 `get` 数值响应是 `71 <4字节小端数值> FF FF FF`，应按固定长度读取，不能仅寻找第一个 `FF FF FF`。

建议单独处理协议解析，避免原生错误应答污染下一条 `VIEW/ALPHA/...`。

当前业务协议**没有请求序号，也没有在确认中携带参数值**。快速连续调节时，板端应按顺序处理或合并到最新目标，避免较早请求的完成结果被显示成较新请求的确认。建议对每个功能维护“最新请求值”和“实际生效值”，仅在二者匹配时确认当前请求；失败和中间状态同样要避免覆盖后续操作。

## 7. 板端发送函数示例

以下仅示范 TJC 指令封装，不包含任何硬件寄存器假设。`uart_write_all` 由板端实现，要求返回前已复制或发送全部数据；若 UART 使用异步 DMA，应自行管理发送缓冲区生命周期。

```c
#include <stddef.h>
#include <stdint.h>
#include <string.h>

/* Board implementation: send/copy exactly len bytes. */
extern void uart_write_all(const uint8_t *data, size_t len);

/* Call only from one serialized TX task/queue. */
static void hmi_cmd(const char *ascii)
{
    static const uint8_t end[3] = {0xFF, 0xFF, 0xFF};
    uart_write_all((const uint8_t *)ascii, strlen(ascii));
    uart_write_all(end, sizeof(end));
}

/* Example: call after real stop completion, with page0 active. */
static void hmi_report_stopped_page0(void)
{
    hmi_cmd("page0.rstatus.txt=\"STOPPED\"");
    hmi_cmd("page0.runreq.val=0");
    hmi_cmd("page0.rack.en=0");
    hmi_cmd("page0.run.val=0");
}
```

同一 UART 的多个发送方应串行化，确保指令与结束符不会被其他数据插入。旧固件面向串口终端的普通日志，应迁移到独立调试通道，或在 HMI 通道上做明确的输出适配。
